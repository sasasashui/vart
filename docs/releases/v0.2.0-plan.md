# VART 0.2.0 development plan

## Status

This document records the proposed scope after the v0.1.0 milestone. It is a
planning baseline, not an instruction to begin implementation. Development of
this milestone starts only after the v0.1.0 code audit is complete and its
findings have been resolved or explicitly deferred.

## Milestone goal

VART 0.2.0 will establish the PCIe, virtio, DMA, and asynchronous I/O
foundation needed by modern virtual devices. The target observable result is a
RISC-V Linux guest that:

- enumerates a PCIe hierarchy;
- receives PCIe MSI-X interrupts through IMSIC;
- mounts a root filesystem from a virtio-blk PCI function;
- exchanges basic network traffic through a virtio-net PCI function; and
- uses eventfd-based notification and independent I/O processing instead of
  routing every data-path notification through the main polling loop.

Correctness, bounded guest input handling, deterministic tests, and clean
teardown remain more important than peak throughput.

## Planned stages

### Stage 10: asynchronous execution foundation

Extend the project-owned event API with monotonic timers, deferred work, an
eventfd notifier, an epoll backend, completion queues, blocking worker pools,
I/O contexts, and independently managed I/O threads. Device interfaces must
remain independent of epoll, io_uring, GLib, and any particular worker model.

The initial implementation does not require coroutines or io_uring. Those can
be added behind stable VART interfaces after the basic lifecycle and
cancellation rules are tested.

### Stage 11: PCIe host bridge and bus model

Implement PCI domains, buses, devices, functions, requester IDs, ECAM
configuration access, type 0 and type 1 headers, multifunction devices, PCI
capabilities, bridges, and recursive bus numbering. Support 32-bit and 64-bit,
prefetchable and non-prefetchable BARs, including sizing probes, enablement,
relocation, and dynamic address-space mappings.

The RISC-V virt machine will expose a QEMU-compatible PCIe host bridge layout
and device-tree node where practical. PCI topology remains distinct from the
system address space; BAR contents continue to use `VartMemoryRegion`.

### Stage 12: PCIe interrupts and KVM notification fast paths

Implement INTx routing through APLIC and MSI/MSI-X routing to IMSIC. Add KVM
interrupt routing, irqfd, ioeventfd, masking, pending state, resampling where
required, reset, and failure cleanup. A small VART-only PCI test function will
validate configuration, BAR, DMA, INTx, MSI, and MSI-X paths before a complex
device depends on them.

### Stage 13: DMA and IOMMU-ready interfaces

Require every DMA master to use its attached DMA address space. Add PCI
requester identity, checked DMA read/write and map/unmap operations,
scatter-gather helpers, permission and overflow checks, mapping lifetime
rules, fault reporting, and IOTLB invalidation hooks.

This stage prepares for a RISC-V IOMMU but does not implement its translation
architecture. A virtio PCI function is a normal PCI requester and can later be
placed behind the RISC-V IOMMU. Virtio IOMMU is a separate device model and is
not required for that arrangement.

### Stage 14: shared virtio core and PCI transport

Implement the virtio 1.x device state machine, feature negotiation, split
virtqueues, indirect descriptors, event index, queue reset, strict descriptor
validation, and the modern virtio-pci transport. Provide common, notify, ISR,
and device configuration regions, per-queue MSI-X vectors, ioeventfd kicks,
and irqfd completions.

Legacy virtio, packed virtqueues, live-migration compatibility, and optional
advanced features are outside the initial milestone.

### Stage 15: virtio block device

Add a transport-independent block backend, initially backed by raw files.
Support capacity discovery, read, write, flush, read-only media, short I/O,
failure propagation, queue draining, and safe teardown. Blocking operations
may initially use the worker infrastructure before an io_uring backend exists.

Complete this stage by booting Linux from a virtio-blk PCI root filesystem.
QCOW2 support is not required.

### Stage 16: virtio network device

Add a transport-independent network backend and an initial TAP backend.
Implement the minimum virtio-net RX and TX paths, link and MAC state, queue
notification, and bounded packet handling. Start with a conservative feature
set before adding checksum, segmentation, or multiqueue acceleration.

Complete this stage with deterministic packet tests followed by basic Linux
network connectivity.

## Cross-cutting requirements

Each stage must preserve the existing VM big-lock rules and document new lock
ownership and ordering before adding finer-grained locks. Blocking I/O must not
hold the big lock. Completion delivery, cancellation, reset, queue draining,
and teardown must be designed together rather than added as error-path fixes.

Tests must cover malformed guest descriptors and configuration accesses,
address and length overflow, reset, resource exhaustion, concurrent shutdown,
and partial initialization cleanup. Add observability for queue operations,
kicks, completions, interrupts, DMA faults, and backend errors without making
device semantics depend on tracing.

## Deferred work

The following remain important candidates for later milestones:

- e1000e emulation as a conventional PCIe network device;
- an NVMe controller with admin and I/O queues, PRP handling, and MSI-X;
- a RISC-V IOMMU with device-directory lookup, page-table walking, IOTLB,
  invalidation, fault reporting, and MSI translation;
- io_uring and coroutine backends after the asynchronous API is stable;
- packed virtqueues and advanced virtio offloads;
- PCIe hotplug, migration, and snapshots; and
- VFIO assignment after PCIe, DMA isolation, reset, interrupt routing, and
  host RISC-V kernel support are sufficiently mature.

These deferred devices must reuse the PCIe, DMA, interrupt, backend, and event
interfaces established by this milestone rather than introducing private data
paths.

## Review and implementation method

Every stage will be divided into small, independently reviewable increments.
Each increment must leave the tree buildable, add a focused unit, integration,
or tiny-guest test, update affected design documentation, and produce one
coherent Linux-style commit. Stage numbering and detailed subdivisions may be
refined after the v0.1.0 audit, before implementation begins.
